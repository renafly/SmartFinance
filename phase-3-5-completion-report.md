# SmartFinance Codebase Cleanup — Phases 3-5 Completion Report

Phases 1 and 2 were reported and executed earlier. This covers Phases 3, 4, and 5 — the last three phases of the original `codebase-cleanup-audit.md` plan. Everything below is applied to your working tree, uncommitted, and verified with babel-parse + JSON-parse + scoped `git diff` after every batch (this sandbox can't run `tsc`/`jest`/`npm install` reliably over the device bridge, so those are still yours to run).

## Phase 3 — duplicate-code consolidation

20 files edited, 2 new shared files added, net 77 insertions / 149 deletions.

**Category grouping.** Extracted a shared `groupCategoriesByParent()` helper and pointed both `category-picker.tsx` and `wage-flow-config-panel.tsx` at it. The wage-flow panel's own version had a real gap — it only grouped by direct parent, so a category three or more levels deep would silently vanish from its multi-select instead of showing up under its top-level ancestor like everywhere else in the app.

**Local-date formatting.** Five near-identical `Date → "YYYY-MM-DD"` functions plus a matching parse pair are now one canonical `getLocalCalendarDate`/`parseLocalCalendarDate`. While comparing them I found a genuine bug, not just duplication: `transfers/utils.ts`'s `today()` built the date via `toISOString()`, which converts through UTC first. Anyone in a US timezone opening "new recurring transfer" in the evening was getting tomorrow's date as the default. That's fixed now as part of the consolidation — flagging it clearly as a behavior fix, not a no-op refactor. Also trimmed a dead import in `transactions.tsx` (two date-formatting functions were imported but never called).

**`roundMoney`.** `saving-pots/services/saving-pot-forecast.service.ts` had a byte-identical duplicate — swapped for canonical, zero risk. `wage-flow.ts`'s copy is missing canonical's `Number.isFinite` guard and is used at 10 call sites — I deliberately left this one alone. I traced a plausible reason it might matter in production: your `transactions.amount` column is `numeric(14,2)`, which PostgREST serializes as a *string* on direct `.select()` queries, and while `transactions.tsx`/`transfers.tsx` explicitly coerce with `Number(...)`, the wage-flow allocation pipeline doesn't — it relies on `as any` casts. I can't confirm this actually produces `NaN` in your data without a runtime check, so per your standing instruction ("if uncertain, don't delete, flag it"), this one stays as-is. Worth a look before you ever touch it.

**Ownership/grouping sentinels.** Swapped the "shared account" sentinel constant in `replenishments/member-grouping.ts` and `grouped-destination-select.tsx` onto the canonical one in `account-ordering.ts` — safe, no visible change. I left the *sort policy* alone (see Phase 4e below) since that's a visible UI difference, not a refactor.

**`TransactionType`.** Created one canonical type at `src/types/transaction-type.ts`. The audit found 2 identical duplicate declarations — while doing the swap I found 2 more it had missed (`recurring-transactions.service.ts`, `transactions.repository.ts`), for 4 total, now consolidated. The unrelated `transfers/types.ts` version (`'income' | 'expense'`, a different concept that happened to share a name) is renamed to `MovementTransactionType` so the collision can't bite anyone again.

## Phase 4 — legacy architecture cleanup

**Deleted the dead Monthly Budget chain** (~357 lines): `monthly-budget/hooks/index.ts`, `monthly-budget/services/monthly-budget.service.ts`, and `repositories/monthly-budget.repository.ts`, plus the three now-dangling references in `repositories/index.ts`'s barrel. The audit flagged this as only "probably safe" because the deleted code's own doc comment claimed the forecast and saving-pots features still depended on it — I checked that claim directly rather than taking it on faith, and it's false: zero references anywhere, and the migration file the comment cited as the reason this code was supposedly still needed doesn't exist. `household-backup.service.ts`, which does need some of the same tables for exporting old backups, does its own independent querying and isn't affected. `monthly-budget/types.ts` and `ui-utils.ts` are still genuinely used elsewhere and were kept.

**NativeWind/Tailwind and Unleash — investigated, not touched.** Both are product decisions, not cleanup calls. NativeWind is fully wired (Metro config, `global.css`, five packages) but only one file anywhere uses `className=`, and even that's hand-written CSS, not a Tailwind utility. Unleash is fully wired too, but its only feature flag has zero call sites and the `.env` keys for it are blank. Either commit to using these or strip them — I didn't choose for you.

**i18n cleanup — 209 translation keys removed** from both `en` and `pt` locale files (they stayed structurally identical throughout, verified). I wrote a small script to re-derive the unused-key list fresh, since the repo had moved since the original audit — it now also correctly resolves i18next's `_one`/`_other` plural-suffix pairs to their base key and tracks dynamic template-literal key construction (things like `` t(`recurring.frequencies.${item.frequency}`) ``), so a key that's only reached dynamically doesn't get flagged as dead. I caught one real mistake of my own mid-pass: my first script version treated two array-valued translation keys (`landing.features.items`, `landing.steps.items`, each accessed via `` t(`...items.${index}.title`) ``) as ordinary unused strings and deleted them. I caught it on the diff review before moving on, restored both from git history, and fixed the script so any array-valued key is now always held out for manual review instead of auto-deleted. `settings.*` (48 keys) and `onboarding.*` (38 keys) are the two largest remaining unused buckets — I deliberately left both alone, same reasoning as the original audit: onboarding's copy moved to hardcoded literals in `guides.ts` on purpose, and settings is large enough to deserve a human pass rather than a bulk delete. One new finding along the way: `settings.*` has its own near-exact copies of the generic action words already deduped in Phase 1 (`settings.sending`, `.creating`, `.saving`, etc., mirroring the root-level `sending`/`creating`/`saving`) — also dead, worth folding into whoever does that settings.* review.

**Transfers and storybook orphan routes — confirmed, not touched.** `transfers.tsx`'s drawer entry is intentionally hidden with a comment claiming Settings links to it "same pattern as Transfers" — but Settings only links to Feedback and Admin Feedback, never to Transfers. I couldn't find any button, link, or navigation call anywhere in the app that reaches the Transfers screen. It's not dead code (the file's exports are used elsewhere), just seemingly unreachable as its own screen. `storybook.tsx` still looks like an intentional URL-only dev page. Both are yours to decide on.

**Ownership sort-policy divergence — confirmed, not touched.** Everywhere else in the app, accounts and members are ordered by a caller-supplied rank array (real household order) with a fixed account-type priority. The wage-flow multi-select panel and the replenishments member grouping both instead sort "Shared last, then alphabetical." Same data, different on-screen order depending which screen you're on — a real, visible inconsistency, but changing it is a product call, not a cleanup.

## Phase 5 — config and database

**Fixed three small config issues.** `eslint.config.js` now ignores `_to_delete/`, `graphify-out/`, and `test-results/` (it was only ignoring `dist/` before, so lint was likely running over scratch/generated content). `app.config.ts`'s app-name fallback was literally the string `"eas credentials -p android"` — an accidental copy-paste, harmless today since `app.json` always sets the real name first, now fixed to `"Kintally"`. `AGENTS.md`'s instruction to always run `graphify query` before anything else was actively misleading every session that opened this repo — the `graphify` binary isn't installed anywhere, even though its stale output directory exists (which is what the doc's own condition checks for). I added a check-once guard and widened the "skip Graphify" rule rather than deleting the section outright, in case a real CLI gets installed later.

**Documented 4 env vars** that were being read by real code but missing from `.env.example`: `EXPO_PUBLIC_COMMIT_SHA` and `EXPO_PUBLIC_RELEASE_CHANNEL` (CI/build-injected, shown in your release diagnostics screen), and `CRON_SECRET`/`SUPABASE_URL` (Vercel deployment vars for the recurring-transactions cron function — note `SUPABASE_URL` is a different variable from the client-side `EXPO_PUBLIC_SUPABASE_URL`, easy to mix up).

**Reported, not acted on:**
Your `.env` is missing `EXPO_PUBLIC_WEB_PUSH_VAPID_PUBLIC_KEY` and `GOOGLE_SERVICES_JSON`, both of which real code reads — web push and the Android Firebase build are likely non-functional right now, which may or may not be expected depending on where you are with those.
Five `.env` keys are set but never read anywhere in code: `EXPO_PUBLIC_SENTRY_DSN` (there's no Sentry package installed either, consistent with a removed integration), plus four Google OAuth client-ID variants and a Supabase redirect URL. Worth confirming these are placeholders for planned work before removing them.
On the database side: I re-confirmed, this time with a precise query-level grep rather than just name matches, that `budget_configs`, `budget_rules`, `budget_rule_allocations`, `monthly_budget_runs`, and `monthly_income_inputs` are read by exactly one file in your whole app layer — `household-backup.service.ts`, for exporting old backups — and that's still true after this session's Monthly Budget deletion. `feedback_events` and `user_keypairs` still show zero references anywhere in the app code. I don't have database access from this sandbox, so any schema-level decision on these tables needs your own verification — nothing here is a recommendation to drop anything.
