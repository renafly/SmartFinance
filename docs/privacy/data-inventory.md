# SmartFinance privacy and data inventory

Status: code-verified inventory, 2026-07-30. This is an engineering record, not a legal conclusion.

## Evidence convention

- **Verified** means the repository directly establishes the fact.
- **Inferred** means the purpose follows reasonably from the feature or field name, but needs product/legal confirmation.
- **UNKNOWN** means the repository does not establish the answer.

Primary evidence reviewed: `supabase/migrations/`, `supabase/functions/`, `src/types/database.types.ts`, Supabase/auth client configuration, repositories and feature services, browser/device persistence modules, notification code, feedback code, and `package.json`. The inventory describes implemented code; it does not prove which environment variables, scheduled jobs, providers, or migrations are active in production.

## Data flows

1. A user authenticates with Supabase Auth, optionally using Google OAuth; the app persists the returned session through `AsyncStorage`.
2. The client sends authenticated database, Storage, RPC and Edge Function requests to Supabase.
3. Household invitations send recipient identity and invitation content from a Supabase function to Resend.
4. Native notification delivery sends Expo push tokens and notification content from a Supabase function to Expo's push API.
5. Web push delivery stores subscription endpoint/key material in Supabase; the actual delivery implementation/provider must be verified from deployed functions/configuration.
6. Feedback and screenshots are sent to Supabase database/Storage; feedback email delivery is represented by an outbox, but the deployed email sender/provider must be confirmed.
7. With analytics consent, the web client loads Vercel Speed Insights.
8. When configured, the client contacts an Unleash proxy every 30 seconds for feature flags. No explicit user identifier/context is supplied by application code.
9. A household backup places a broad copy of household and financial data into a user-controlled export file.

## Verified safeguards

- RLS is enabled for the reviewed user-facing tables, with hardening migrations and private Storage bucket policies present.
- Attachment and feedback screenshot buckets are configured as private in migrations.
- Supabase publishable/anonymous credentials are used in client code; code comments prohibit a service-role key in the client.
- Analytics is gated on the stored analytics-consent choice.
- Feedback input has field/JSON/file-size limits, rate limits and explicit cleanup functions.
- Many core records cascade on profile or household deletion.

These are code-level observations, not proof that production migrations, jobs and environment settings match the repository.

## Required legal/business and production inputs

- Controller legal name, address, privacy contact, representative and DPO decision.
- Exact production Supabase project region, Auth providers/settings, JWT/session lifetimes, backups, point-in-time recovery, logs and deletion behavior.
- Whether Vercel Speed Insights, Unleash, Expo push, Resend and web push are enabled in production, plus their configurations.
- Purpose/legal-basis decision for every row above; contract/legitimate-interest/consent labels must be made with counsel, not inferred from code.
- Precise retention schedule for all records marked **UNKNOWN**, including backups and logs.
- Account deletion/export workflows, shared-household conflict rules, and evidence of downstream processor deletion.
- Data-access roles, support/admin procedures and production RLS verification.
- International-transfer locations and safeguards for every processor/subprocessor.
- Whether a DPIA is required for the scale, monitoring and nature of financial-data processing.

## Highest-risk gaps

1. There is no complete, approved retention schedule; audit logs and invitation delivery logs have no repository-defined purge.
2. `audit_logs.old_data` and `new_data` can preserve full financial records after source records or direct identifiers are removed.
3. Production regions, subprocessors, DPAs and international-transfer safeguards are not evidenced.
4. Account deletion does not, from this client repository alone, prove deletion from Auth, backups, logs and all processors.
5. Notification bodies, arbitrary JSON metadata, feedback screenshots and support text can contain unexpected sensitive data; minimization/redaction rules are not documented.
6. The production activation and execution of scheduled deletion jobs is unverified.
7. Authentication tokens are JavaScript-accessible; this is not itself a cookie-law defect, but it raises the impact of XSS and warrants CSP/security testing.
