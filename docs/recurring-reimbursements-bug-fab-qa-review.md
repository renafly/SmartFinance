# QA review — recurring end-conditions, reimbursements, bug-report FAB

Cross-review of `docs/recurring-end-conditions-reimbursements-bug-fab-plan.md` and its implementation, against the edge cases called out in the original QA prompt. One finding was CONFIRMED and fixed during this pass (found by reading the diff, not by running the app); everything else was checked by reading the code/schema.

## 1. Recurring end-conditions

| # | Case | Result |
|---|---|---|
| 1.1 | Rule anchored on the 31st, monthly frequency — what happens in February? | **Pre-existing, not introduced here.** `next_recurring_occurrence()` (migration `20260710000400`) does plain `date + interval '1 month'`, which Postgres resolves by overflow (Jan 31 → early March, skipping Feb entirely) rather than clamping to Feb 28/29. This function is shared with `budget_rules.frequency`, so changing its semantics is a product decision with a bigger blast radius than this feature. Left unchanged; flagged in the plan doc §1.4 and here for visibility. **Recommendation**: decide the intended behavior (clamp to last day of month vs. current overflow) as its own follow-up, since it affects monthly budget rules too. |
| 1.2 | `end_after_occurrences = 1` | **Correct.** Verified by both the check constraint (`> 0`, so 1 is valid) and the RPC: the occurrence that brings `occurrences_count` to 1 is generated, *then* `is_active` is set false in the same update. Unit-tested in `recurring-transactions.service.unit.test.ts`. |
| 1.3 | Timezone in generation | No new risk. The added `end_condition = 'date'` check compares two plain `date` columns (`next_run > end_date`), which carry no time-of-day/timezone component — same footing as every other `next_run` comparison already in the function. The scheduler's own as-of date still comes from `timezone('Europe/Lisbon', now())::date`, unchanged. |
| 1.4 | Edit/delete only affects future occurrences | **Verified against the existing FK chain**, not newly built: `recurring_run_executions.recurring_transaction_id` is `on delete cascade`, but `transactions.recurring_execution_id` is `on delete set null`. Deleting a rule cascades away its execution-tracking rows and only unlinks (never deletes) the `transactions` rows already generated. Editing only changes the template read on the *next* run. No code changes were needed for this guarantee. |

## 2. Reimbursements

| # | Case | Result |
|---|---|---|
| 2.1 | Over-reimbursement correctly reduces the monthly total (not floored at zero / not ignored) | **Correct.** `monthly_summary.expenses` and `monthly_category_spending.total` both sum `transaction_effective_amounts.effective_amount`, which is `amount - reimbursed_total` with no floor — a negative effective amount subtracts from (i.e. reduces) the month's expense total, exactly as specified. |
| 2.2 | Multiple reimbursements on one expense sum correctly | **Correct.** `transaction_effective_amounts` sums via `group by transaction_id` server-side; `computeEffectiveAmount()` sums client-side in integer cents. Unit-tested with 3 payers on one expense and with classic float-noise inputs (0.1 + 0.2). |
| 2.3 | A 0-value reimbursement must not create a phantom entry | **Correct, enforced twice.** DB: `amount numeric(14,2) not null check (amount > 0)` rejects it outright. Client: `validateReimbursementDraft` rejects it before the request is even sent, so the form surfaces a clear error instead of a raw constraint violation. |

## 3. Floating bug-report button

| # | Case | Result |
|---|---|---|
| 3.1 | Doesn't block clicks on other elements | **CONFIRMED bug, fixed.** The first implementation placed the FAB at a fixed bottom-right offset (`right: spacing(2.5)`, `bottom: insets.bottom + spacing(2.5)`) on every screen. Two screens already render their own fixed bottom overlay via `Page`'s `overlay` prop (confirmed by grepping for `overlay=` across `src/app/(protected)`): `/transactions` has its own bottom-*right* "Add transaction" pill at `right: spacing(6), bottom: spacing(6) + insets.bottom` — nearly the same corner and offset, which would have sat underneath (and intercepted taps meant for) that pill on the app's busiest screen. `/budget` has a *full-width* bottom action bar (1-3 buttons that can wrap, plus an optional two-line hint) whose height can't be known from source alone, so no fixed offset is safely guaranteed to clear it. **Fix**: `bug-report-fab.tsx` is now route-aware — it renders at bottom-*left* on `/transactions` (that screen's overlay is right-anchored, not full-width, so the left corner is free) and doesn't render at all on `/budget` (the drawer menu still reaches Feedback from there). See the component's own doc comment for the reasoning, so a future screen adding a conflicting `overlay` has a clear place to extend the exclusion list. |
| 3.2 | Destination route exists | **Correct.** `/feedback` (`src/app/(protected)/feedback.tsx`) is the app's existing, working bug-report screen — not a new route. The FAB pushes `/(protected)/feedback?kind=bug`, and `feedback.tsx` now reads `kind` via `useLocalSearchParams` to preselect the bug tab. |

## 4. Bug found and fixed during this review

**Severity: critical.** `recurringTransactionsService.createRecurringTransaction`/`updateRecurringTransaction` expect `input.endCondition` to be a single object (`{ endCondition: 'count', endAfterOccurrences: 12 }`, etc.). Both call sites in `src/app/(protected)/transfers.tsx` (`recurringPayload()`, used by both create and edit, and `RecurringTransferCreateForm`'s own `save()`) originally built the payload with `...endConditionPayload(draft)` — a *spread* — which flattens those keys onto the top-level payload instead of nesting them under `endCondition`. At runtime this would have made `input.endCondition` end up as the bare string `'count'`/`'date'` (or left the real value dropped entirely), and `resolveEndConditionColumns` would have thrown `Unknown endCondition: undefined` for any rule created or edited with a non-"never" end condition — i.e. the end-condition feature would have been broken for every user-facing save path except "never" (the default). **Fixed**: both call sites now use `endCondition: endConditionPayload(draft)` (a field assignment, not a spread). Re-verified with an isolated Babel parse of the file after the fix.
